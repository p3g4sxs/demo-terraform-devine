Módulo 01 · Principiante

¿Qué es Terraform?

Infraestructura como Código (IaC)

Este módulo es para todos, incluyendo gerentes. No asuman conocimiento previo. Comiencen con una pregunta al auditorio: ¿alguien ha creado un servidor en AWS manualmente? ¿Cuánto tardaron? ¿Podrían repetir exactamente los mismos pasos? Esa respuesta lleva al problema que Terraform resuelve.

El problema sin IaC

❌ Antes (manual)

  • Clic a clic en la consola AWS
  • Pasos documentados en Word
  • Nadie sabe qué creó quién
  • Imposible de reproducir exacto
  • Sin historial de cambios
  • Dev ≠ Staging ≠ Producción

✅ Con IaC (Terraform)

  • Infraestructura definida en código
  • Versionada en Git
  • Revisada en Pull Requests
  • Reproducible siempre
  • Historial completo de cambios
  • Dev = Staging = Producción
Aquí pueden contar una anécdota real del equipo si tienen una: "¿recuerdan cuando X pasó a producción y el ambiente era diferente al de staging?" Ese es el problema del lado izquierdo. Para los gerentes: el lado derecho significa menos incidentes nocturnos, menos tiempo de onboarding para nuevos devs, y ambientes predecibles. El código de infraestructura se revisa igual que el código de la aplicación — eso es control y trazabilidad.

¿Qué es Terraform?

📖 Definición

Herramienta open-source de HashiCorp que permite definir, provisionar y gestionar infraestructura en la nube usando un lenguaje declarativo: HCL (HashiCorp Configuration Language).

🎯 Declarativo vs Imperativo

Imperativo: "Crea el servidor, configura el puerto 80, agrega el certificado..."
Declarativo: "Quiero un servidor web con SSL activado." — Terraform decide el cómo.

☁️ Multi-cloud

Un solo lenguaje para AWS, Azure, GCP, Kubernetes, Datadog, GitHub y más de 3,000 providers.

La analogía que funciona bien con gerentes: Terraform es como un arquitecto que tiene un plano. El plano dice qué debe existir. Terraform compara ese plano con la realidad y construye solo lo que falta. Si cambian el plano, Terraform sabe exactamente qué demoler, qué construir y qué dejar igual. Para los devs: piensen en Docker Compose pero para infraestructura cloud. Declaran el estado deseado y Terraform lo lleva allá. Dato importante: HashiCorp fue adquirida por IBM en 2024, pero Terraform sigue siendo la herramienta estándar de la industria. OpenTofu es el fork open-source si en el futuro hay cambios de licencia.

Terraform vs otras herramientas

HerramientaTipoAlcanceCurva de aprendizaje
TerraformDeclarativoMulti-cloudMedia ⭐
CloudFormationDeclarativoSolo AWSAlta
AnsibleImperativoConfig MgmtMedia
PulumiImperativo (código)Multi-cloudMedia
ARM TemplatesDeclarativoSolo AzureAlta
La pregunta que siempre surge: ¿por qué Terraform y no CloudFormation si ya usamos AWS? Respuesta: porque el día que quieran tocar algo en Azure, o usar un proveedor de DNS, o gestionar GitHub, Terraform ya lo cubre. No están atados a un solo cloud. Ansible es complementario — Terraform crea la infraestructura, Ansible configura lo que hay dentro. Pulumi es interesante para equipos que quieren escribir infraestructura en TypeScript o Python, pero la comunidad y el ecosistema de Terraform son mucho mayores hoy en día. Pregunta dinámica: ¿alguien del equipo ya usó alguna de estas herramientas?
Módulo 02 · Principiante

HCL — El lenguaje de Terraform

Providers · Resources · Variables · Outputs

HCL no es un lenguaje de programación completo. Es un lenguaje de configuración — muy legible, parecido a JSON pero más amigable. Si alguien del auditorio sabe leer un archivo de configuración, va a entender HCL en minutos. Antes de pasar a los bloques, muestren la estructura del proyecto — eso da contexto de dónde vive cada cosa.

Estructura del proyecto

📁 Archivos mínimos

mi-proyecto/
├── providers.tf    # Configura el cloud
├── main.tf         # Recursos principales
├── variables.tf    # Definición de vars
├── outputs.tf      # Qué muestra al final
└── terraform.tfvars # Valores por ambiente

📁 Proyecto real (este)

terraform-capacitacion/
├── backend.tf       # Remote state (comentado)
├── providers.tf     # AWS + profile
├── main.tf          # S3 + CloudFront
├── variables.tf     # Variables tipadas
├── outputs.tf       # URL del portal
├── terraform.tfvars # Valores de la demo
└── web/             # Archivos del portal
Muestren el repositorio real en Azure DevOps o el directorio local en la terminal. La idea es que la audiencia vea que no hay magia: son archivos de texto planos. El de la izquierda es el mínimo para empezar. El de la derecha es el proyecto que desplegamos hoy. Señalen: backend.tf está comentado porque en la demo usamos state local — luego en el módulo de state explicamos por qué en producción lo tenemos habilitado con S3.

Bloque: provider

Le dice a Terraform con qué nube hablar y cómo autenticarse

providers.tf
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"    # Al menos 5.x, no 6.x
    }
  }
}

provider "aws" {
  region  = var.aws_region   # Variable — no hardcodeado
  profile = "hackaton-aws"   # Perfil del ~/.aws/credentials
}

💡 terraform init

Descarga el provider de AWS (como npm install) y lo guarda en .terraform/. Siempre es el primer comando.

Analogía para todos: el bloque terraform es como el package.json — dice qué versiones necesita. El bloque provider es como configurar la conexión a la base de datos — le dice a Terraform en qué región de AWS trabajar y con qué credenciales. Importante señalar: "profile = hackaton-aws" — eso apunta al archivo ~/.aws/credentials de la máquina local. En el pipeline de Azure DevOps esto se reemplaza por variables de entorno secretas. La versión "~> 5.0" significa: cualquier versión 5.x pero no 6.x. Así evitan sorpresas.

Bloque: resource

La unidad básica — cada recurso de infraestructura que Terraform gestiona

main.tf
# Sintaxis:  resource "TIPO"  "NOMBRE_LOCAL"  { ... }
#                     └─────────────┘  └──────────┘
#                     provider+recurso  tu etiqueta

resource "aws_s3_bucket" "portal" {
  bucket        = "mi-portal-terraform-demo"
  force_destroy = true
  tags = { Environment = "demo", ManagedBy = "terraform" }
}

# Referenciar otro recurso:  TIPO.NOMBRE.ATRIBUTO
resource "aws_s3_bucket_versioning" "portal" {
  bucket = aws_s3_bucket.portal.id   # ← referencia al bucket
  versioning_configuration { status = "Enabled" }
}
El bloque resource es el más importante — aquí vive la infraestructura real. Señalen la sintaxis: "aws_s3_bucket" viene del provider de AWS, "portal" es el nombre que ustedes le dan. Ese nombre solo existe dentro del código de Terraform. La referencia aws_s3_bucket.portal.id es poderosa: Terraform sabe que el versioning depende del bucket y lo crea en el orden correcto automáticamente. No hay que gestionar dependencias manualmente. Pregunta para devs: ¿qué pasa si el bucket ya existe? Terraform lo detecta y hace un update, no un replace. A menos que sea un cambio que obligue a recrear — en ese caso el plan lo dice claramente con "-/+".

Bloques: variable y output

variables.tf
variable "aws_region" {
  type    = string
  default = "us-east-1"
}

variable "environment" {
  type = string
  validation {
    condition = contains(
      ["dev","staging","prod"],
      var.environment)
    error_message = "Solo dev/staging/prod"
  }
}
terraform.tfvars
aws_region  = "us-east-1"
environment = "demo"
portal_bucket_name = "mi-portal"
outputs.tf
output "portal_url" {
  description = "URL del portal"
  value = "https://${
    aws_cloudfront_distribution
    .portal.domain_name
  }"
}

# sensitive oculta en logs
output "db_password" {
  value     = random_password.db.result
  sensitive = true
}

terraform output — todos
terraform output portal_url — uno

Las variables son la clave para reutilizar el mismo código en múltiples ambientes. Noten el bloque validation: Terraform valida los valores antes de hacer cualquier cambio en AWS. Si alguien escribe environment = "produccion" en vez de "prod", el error aparece localmente, no en AWS. El tfvars es el archivo donde ponen los valores reales. Tienen uno por ambiente: dev, staging, prod. Los outputs son lo que ven al final del apply — en la demo vieron la URL del portal aparecer automáticamente. Eso es un output. También sirven para conectar módulos entre sí.
Módulo 03 · Principiante

El ciclo de vida

init · plan · apply · destroy

Este módulo es muy práctico. Si tienen una terminal abierta, es buen momento para mostrar los comandos en vivo y que la audiencia vea la salida real. Cuatro comandos, cuatro conceptos. Al terminar este módulo, cualquier persona debería poder clonar el repo y desplegar.

Los 4 comandos esenciales

📦
terraform init

Descarga providers y módulos. Inicializa el backend. Siempre primero. Seguro de repetir.

🔍
terraform plan

Compara el state con el código. Muestra qué se creará, modificará o destruirá. Solo lectura — no hace cambios.

🚀
terraform apply

Ejecuta el plan y aplica los cambios en la infraestructura real. Pide confirmación. En CI/CD: -auto-approve.

💥
terraform destroy

Elimina todos los recursos gestionados. ¡Irreversible! Solo en demos o ambientes efímeros.

Init: solo se ejecuta una vez al clonar el repo, o cuando cambia el backend. Plan: este es el comando más valioso en producción. Nunca apliquen sin ver el plan primero. Una buena práctica: el plan se guarda como artefacto en el pipeline y se adjunta al PR como comentario. Apply: en local piden confirmación escribiendo "yes". En el pipeline usan -auto-approve, pero solo después de que alguien aprobó el PR y revisó el plan. Destroy: úsenlo al final de esta demo para limpiar. En producción, hay recursos con deletion_protection habilitado (RDS, por ejemplo) que Terraform no puede destruir sin deshabilitarlo primero.

El plan en detalle

Esto es exactamente lo que vieron al inicio de la sesión

$ terraform plan

  # aws_s3_bucket.portal will be created
  + resource "aws_s3_bucket" "portal" {
      + bucket        = "terraform-capacitacion-portal-demo"
      + force_destroy = true
      + id            = (known after apply)
    }

  # aws_cloudfront_distribution.portal will be created
  + resource "aws_cloudfront_distribution" "portal" {
      + domain_name = (known after apply)
      + enabled     = true
    }

Plan: 8 to add, 0 to change, 0 to destroy.
#      └──────┘  └──────────┘  └──────────┘
#      Nuevos    Modificados    Eliminados
+ crear ~ modificar - destruir
Señalen el "known after apply" — algunos valores como el ID o el dominio de CloudFront no existen hasta que el recurso se crea. Terraform lo sabe y lo indica claramente. El resumen final "8 to add, 0 to change, 0 to destroy" es lo primero que deben leer en cualquier plan. Si ven un número inesperado en "destroy", paren y revisen antes de continuar. Actividad dinámica: pídanle a alguien del auditorio que lea el plan de pantalla y explique qué cree que va a pasar. Casi siempre aciertan — eso demuestra que HCL es legible.
Módulo 04 · Intermedio

El State — memoria de Terraform

¿Qué creé? ¿Qué cambió? ¿Qué debo destruir?

El State es el concepto más importante de Terraform y el que más dolores de cabeza causa cuando no se entiende bien. Vale la pena tomarse el tiempo aquí. Comiencen con la pregunta: si Terraform no tiene estado, ¿cómo sabría si ya creó el bucket o no? Esa pregunta lleva directamente a entender por qué existe el tfstate.

¿Qué es el State?

📋 terraform.tfstate

Archivo JSON que Terraform mantiene para saber exactamente qué recursos creó, con qué configuración y con qué IDs en el cloud. Sin el state, Terraform no sabe qué existe.

❌ State local (default)

  • Vive solo en tu máquina
  • El equipo no puede usarlo
  • Sin lock → conflictos
  • Se pierde si borras la carpeta
  • Secretos en texto plano

✅ State remoto (S3)

  • En S3 — accesible por el equipo
  • Lock con DynamoDB → sin conflictos
  • Versionado — historial completo
  • Cifrado en reposo (AES-256)
  • El pipeline CI/CD lo usa igual
Muéstrenle el archivo terraform.tfstate del proyecto en la terminal: cat terraform.tfstate | head -50 La audiencia verá que es JSON puro con los IDs reales de AWS. Eso es lo que Terraform usa para saber qué existe. Escenario de pesadilla con state local: el developer que tenía el tfstate en su laptop sale de vacaciones y nadie más puede hacer un terraform apply porque el state está en su máquina. Con S3: el state vive en la nube, el pipeline lo lee y escribe, y DynamoDB asegura que solo un proceso lo modifica a la vez. Si alguien está haciendo apply en su máquina y el pipeline también intenta aplicar, DynamoDB bloquea al segundo. Sin ese lock podrían tener state corrupto.

Remote State en S3 — nuestro backend.tf

backend.tf
terraform {
  backend "s3" {
    bucket         = "terraform-capacitacion-state"
    key            = "capacitacion/portal/terraform.tfstate"
    region         = "us-east-1"
    profile        = "hackaton-aws"
    dynamodb_table = "terraform-capacitacion-lock"  # lock
    encrypt        = true
  }
}

La key es como la ruta del archivo dentro del bucket. Pueden tener múltiples proyectos en el mismo bucket usando keys diferentes: "proyecto-a/prod/terraform.tfstate", "proyecto-b/dev/terraform.tfstate". El campo encrypt=true es obligatorio en producción — el tfstate puede contener passwords, tokens y ARNs sensibles. En la demo de hoy ese backend.tf está comentado y usamos state local para simplificar. En el repo de Azure DevOps de producción está habilitado. Señalen esa diferencia. Pregunta para arquitectos: ¿cuándo tendría sentido tener un bucket de state separado por proyecto vs. uno compartido con keys diferentes? (respuesta: depende del nivel de aislamiento de permisos que necesiten)

Comandos útiles del State

# Ver qué recursos gestiona Terraform
terraform state list

# Ver detalles de un recurso
terraform state show aws_s3_bucket.portal

# Mover recurso (renombrado en el código)
terraform state mv aws_s3_bucket.old aws_s3_bucket.new

# Importar recurso existente al state
terraform import aws_s3_bucket.portal mi-bucket-existente

# Sacar un recurso del state SIN destruirlo en AWS
terraform state rm aws_s3_bucket.portal

⚠️ Regla de oro

Nunca edites terraform.tfstate manualmente. Usa siempre los comandos terraform state.

terraform state list es el comando de diagnóstico más útil. Muéstrenlo en la terminal en vivo. terraform import es clave cuando el equipo tiene recursos creados manualmente antes de adoptar Terraform. Proceso típico: importar el recurso, luego escribir el código HCL que lo describe, luego hacer plan para verificar que no hay drift. terraform state rm es útil cuando quieren dejar de gestionar un recurso con Terraform sin destruirlo. Por ejemplo, si mueven un recurso a otro proyecto de Terraform. Escenario real para mencionar: "hemos usado terraform state mv cuando renombramos un módulo y el plan mostraba destroy + create. Con el mv evitamos destruir el recurso en producción."
Módulo 05 · Intermedio

Variables y tfvars

Un código, múltiples ambientes

Este módulo responde una pregunta frecuente: ¿cómo usamos el mismo código de Terraform para dev, staging y producción sin duplicar nada? La respuesta son los archivos tfvars. Un código, múltiples configuraciones.

El patrón de ambientes con tfvars

dev.tfvars
environment = "dev"
aws_region  = "us-east-1"
portal_bucket_name =
  "mi-portal-dev"
cloudfront_price_class =
  "PriceClass_100"
tags = {
  Environment = "dev"
}
staging.tfvars
environment = "staging"
aws_region  = "us-east-1"
portal_bucket_name =
  "mi-portal-staging"
cloudfront_price_class =
  "PriceClass_100"
tags = {
  Environment = "staging"
}
prod.tfvars
environment = "prod"
aws_region  = "us-east-1"
portal_bucket_name =
  "mi-portal-prod"
cloudfront_price_class =
  "PriceClass_All"
tags = {
  Environment = "prod"
}

terraform apply -var-file="dev.tfvars"    terraform apply -var-file="prod.tfvars"

Señalen la diferencia entre dev/staging y prod: el PriceClass de CloudFront. En dev usan PriceClass_100 (solo USA/Europa, más barato). En prod usan PriceClass_All (global). Eso es exactamente el tipo de decisión que se maneja en tfvars: misma infraestructura, diferente configuración. En el pipeline de Azure DevOps, el nombre del archivo tfvars se deriva automáticamente del nombre del branch: main → prod.tfvars, develop → dev.tfvars. Muestren eso en el slide del pipeline del módulo 07. Pregunta para el equipo: ¿qué otras diferencias tienen entre ambientes actualmente? Eso abre conversación sobre qué más podría configurarse via tfvars.

Jerarquía de variables

Mayor número = mayor precedencia (sobreescribe los anteriores)

1
default en variables.tf

Valor por defecto si no se pasa ningún otro valor.

2
terraform.tfvars

Se carga automáticamente si existe en el directorio de trabajo.

3
-var-file="prod.tfvars"

Archivo tfvars específico pasado en el comando.

4
Variable de entorno TF_VAR_nombre

export TF_VAR_aws_region="us-west-2" — muy útil en CI/CD para secretos.

5
-var="nombre=valor" en el comando

Máxima precedencia. Sobreescribe todo. terraform apply -var="environment=prod"

Este orden de precedencia evita muchos bugs. El caso más común de confusión: "tengo dev.tfvars pero también tengo un terraform.tfvars y no sé cuál aplica." Respuesta: el -var-file="dev.tfvars" tiene precedencia sobre terraform.tfvars para las mismas variables. Las variables de entorno TF_VAR_ son las que usamos en el pipeline para pasar secretos que no deben estar en ningún archivo del repositorio: passwords de base de datos, tokens de API. El nivel 5 es útil para overrides rápidos en debugging local, pero no en pipelines de producción.
Módulo 06 · Intermedio

Módulos

Reutilización y estandarización de infraestructura

Los módulos son el paso hacia la madurez en Terraform. Un equipo que empieza bien escribe todo en main.tf. Un equipo que escala usa módulos para que la infraestructura común sea consistente en todos los proyectos. Piensen en módulos como las librerías del equipo.

¿Qué es un módulo?

📦 Módulo = carpeta de Terraform

Todo directorio con archivos .tf es un módulo. Permite empaquetar infraestructura reutilizable — igual que una función en programación.

📁 Sin módulos (caos)

proyecto/
├── main.tf  # 800+ líneas
└── ...      # todo mezclado

📁 Con módulos (orden)

proyecto/
├── main.tf             # orquestador
└── modules/
    ├── networking/     # VPC, subnets
    ├── compute/        # EC2, ASG
    ├── storage/        # S3, RDS
    └── cdn/            # CloudFront
Analogía práctica: imaginen que cada proyecto necesita una VPC con sus subnets públicas y privadas. Sin módulos, copian y pegan ese bloque de código en cada proyecto. Con módulos, llaman module "vpc" y pasan los parámetros. Si el equipo de seguridad dice "todas las VPCs deben tener flow logs", lo cambian en el módulo y todos los proyectos lo adoptan al próximo apply. También pueden usar módulos del Terraform Registry — hay módulos oficiales de AWS muy bien mantenidos. Ejemplo: module "vpc" from terraform-aws-modules/vpc/aws — no tienen que escribir la VPC desde cero.

Llamar un módulo

modules/cdn/main.tf
variable "bucket_name" { type = string }
variable "environment"  { type = string }

resource "aws_cloudfront_distribution" "this" {
  # ... configuración
}

output "domain_name" {
  value = aws_cloudfront_distribution
          .this.domain_name
}
main.tf (raíz)
module "portal_cdn" {
  source = "./modules/cdn"

  # Variables al módulo
  bucket_name = var.portal_bucket_name
  environment = var.environment
}

# Output del módulo
output "portal_url" {
  value = "https://${
    module.portal_cdn.domain_name
  }"
}
Noten que el módulo tiene sus propias variables, recursos y outputs — es completamente autocontenido. El main.tf raíz es el orquestador: llama módulos y conecta sus outputs. El source puede ser una ruta local ./modules/cdn, un repositorio Git, o el Terraform Registry. Después de agregar o cambiar un módulo, hay que correr terraform init de nuevo para que Terraform descargue o actualice el módulo. Un patrón muy útil en equipos: tener un repositorio separado solo de módulos internos, y los proyectos los llaman via Git. Así el equipo de plataforma mantiene los estándares centralizados.

Pipeline de Azure DevOps

azure-pipelines.yml
trigger:
  branches: { include: [main, develop] }

variables:
  TF_VAR_FILE: environments/$(Build.SourceBranchName).tfvars

stages:
  - stage: Plan
    jobs:
      - job: TerraformPlan
        steps:
          - task: TerraformInstaller@1
            inputs: { terraformVersion: "1.9.0" }
          - script: terraform init
            env:
              AWS_ACCESS_KEY_ID: $(AWS_ACCESS_KEY_ID)
              AWS_SECRET_ACCESS_KEY: $(AWS_SECRET_ACCESS_KEY)
          - script: terraform plan -var-file=$(TF_VAR_FILE) -out=tfplan
          - publish: tfplan

  - stage: Apply
    dependsOn: Plan
    condition: eq(variables['Build.SourceBranch'],'refs/heads/main')
    jobs:
      - deployment: TerraformApply
        environment: production       # requiere aprobación manual
        steps:
          - download: current
          - script: terraform apply tfplan
Señalen la línea TF_VAR_FILE: automáticamente usa el nombre del branch como nombre del tfvars. El stage Plan corre en todos los branches — así en cualquier PR pueden ver el plan. El stage Apply solo corre en main Y requiere aprobación manual del environment "production" en Azure DevOps. Eso significa que alguien del equipo tiene que hacer clic en "Approve" antes de que se apliquen cambios en producción. El artefacto tfplan asegura que lo que se aplica es exactamente lo que fue revisado — no un plan nuevo. Las credenciales AWS están en variables secretas de Azure DevOps: $(AWS_ACCESS_KEY_ID). Nunca aparecen en el código ni en los logs del pipeline.

Flujo: del commit al recurso AWS

📝
1. Developer hace commit

Modifica un .tf o tfvars y abre un Pull Request en Azure DevOps.

🔍
2. Pipeline: terraform plan

El plan se publica como comentario en el PR. El equipo revisa qué cambia en AWS.

✅
3. Aprobación y merge a main

El arquitecto o tech lead aprueba. Al mergear se dispara el stage de Apply.

🚀
4. terraform apply automático

El pipeline aplica el plan. Los recursos en AWS son creados o modificados.

🪣
5. State actualizado en S3

Terraform actualiza el tfstate en S3. DynamoDB libera el lock.

Este flujo es el GitOps para infraestructura. El repositorio es la fuente de verdad. Nada en AWS debería existir que no esté en el repositorio. Para project managers: cada cambio en infraestructura tiene un PR con su descripción, su revisor, su fecha y su autor. Auditoría completa sin esfuerzo extra. Para developers: el flujo es el mismo que para el código de la aplicación. Git, PR, review, merge. Ya saben hacerlo. Pregunta para el auditorio: ¿qué pasa si alguien hace un cambio manual en la consola de AWS sin pasar por Terraform? (respuesta: el próximo plan detecta el drift y puede revertirlo)

Replica este portal

Paso a paso desde cero

Prerequisitos

🔧
1. Instalar Terraform

macOS: brew install terraform  ·  Windows: choco install terraform  ·  Verificar: terraform version

🔑
2. Configurar credenciales AWS

Archivo ~/.aws/credentials
[hackaton-aws]

📁
3. Clonar el repositorio

git clone <url-repo-azure-devops>   entonces   cd terraform-capacitacion

✏️
4. Ajustar terraform.tfvars

Cambia portal_bucket_name — debe ser único globalmente en AWS.
Ej: "terraform-capacitacion-portal-tu-nombre"

Si alguien no tiene AWS CLI instalado, también pueden verificar con: aws sts get-caller-identity --profile hackaton-aws Si devuelve el Account ID, las credenciales están bien configuradas. Bonus

Buenas prácticas

Lo que aprendemos trabajando con Terraform en producción

Este slide es opcional según el tiempo disponible. Son las lecciones aprendidas del equipo — no son teóricas. Si tienen tiempo, conversen sobre cada una y pregunten si alguna les ha quemado antes.

10 reglas que evitan dolores de cabeza

01 Siempre revisa el terraform plan antes del apply
02 Remote state en S3 con DynamoDB lock desde el día 1
03 Usa tfvars por ambiente — nunca hardcodees valores
04 Agrega tags a todos los recursos (costos, responsable)
05 Nunca borres ni edites el tfstate manualmente
06 Versiona tus providers — evita rangos abiertos
07 Usa módulos para infraestructura que se repite
08 Code review obligatorio para cambios en producción
09 Las credenciales van en variables de entorno, nunca en el código
10 Agrega .gitignore — nunca subas .terraform/ ni *.tfstate
Recorran las 10 rápido y deténganse en las que el equipo ha vivido en carne propia. La 01 parece obvia pero en la práctica la presión del tiempo lleva a saltársela — y ahí ocurren los accidentes. La 04 sobre tags es clave para los gerentes: sin tags no pueden saber qué recursos pertenecen a qué proyecto en la factura de AWS. Con tags pueden filtrar costos por equipo, por ambiente, por proyecto. La 09 es la más crítica de seguridad: un access key en un repositorio Git puede costar miles de dólares si un bot lo detecta y lo usa para minar crypto. GitHub y Azure DevOps tienen scanners que detectan esto. La 10: si alguien sube .terraform/ al repo, están subiendo los binarios del provider (cientos de MB) al Git. Si suben *.tfstate, están publicando IDs, ARNs y posiblemente secretos de producción.
